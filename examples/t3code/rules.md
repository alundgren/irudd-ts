# T3 architecture rule catalog

The default preset at [`examples/t3code/profiles/t3code.json`](profiles/t3code.json) contains 25 configured rule instances. That is a count of preset entries, not 25 observed defects or 25 independent historical fixes. The two mobile presets and the exploratory/legacy presets add separate entries with narrower scope.

The separate [structural profile](profiles/t3code-structure.json) has nine configured file roles and eleven rules. It checks scoped classification, service/layer and toolkit companions, migration import prerequisites, exports and role dependencies. Its independently authored simulation is described in [repository-structure.md](../../research/t3code/structure.md); it is an adoption candidate with synthetic controls, separate from historical defect counts.

## Additional presets

- **Mobile platform cycles:** `t3code-mobile-android.json` and `t3code-mobile-ios.json` each define one platform-specific `noCycles` rule with type imports included. PR #13151 is direct regression evidence: `FilePreviewModal.tsx` imported `FilePreview`, while the selected `FilePreview.tsx` or `FilePreview.ios.tsx` imported a type back from the modal. The fix extracted `FilePreviewModal.types.ts`; merge `5821b778fd29e9c5b6945f4e7150f92d19a0a3da` (main). Current `apps/mobile/src/dependency-graph.test.ts` already checks static cycles under iOS and Android resolution. The preset overlaps that CI test. Dynamic imports are excluded from cycle detection, though the existing test counts them for cross-layer ceilings; declaration files, test/test-support files and opposite-platform source files are excluded.
- **Legacy boundary:** `t3code-legacy-boundary.json` encodes a real V2 migration policy from PR #14018: V1 table readers live in the importer/migrations (with a checked `serverSettings.ts` exception), and imports from `orchestration-v2/legacy/` are limited to `ThreadManagementService.ts`, `runtimeLayer.ts`, `ProjectService.ts`, and `serverRuntimeStartup.ts`. Upstream tests also forbid additional `projection_thread_messages` readers; this preset enforces importer dependency paths and retired imports only. It does not inspect SQL table reads. Merge `babea405ec5149121979e7545990c458f5c0d2e6` (V2 workstream). This is historical branch-specific policy: the reviewed checkout still has `apps/server/src/orchestration/decider.ts` and does not contain the V2 legacy-importer paths, so enabling this preset on that checkout would produce invalid findings.
- **Experimental:** `unique-service-identifiers`, `domain-no-reachable-runtime`, and `workspace-service-layer` are explorations, not confirmed historical defects. T3 uses `Context.Service` identifiers and `WorkspacePaths` as a service reference (`docs/internals/effect-services.md:36–64`), but no reviewed PR established duplicate service IDs or a missing workspace layer as a bug. PR #2851 renamed identifiers for TypeScript-Go naming requirements, not to fix a duplicate-ID incident. Treat the three rules as experiments requiring observed findings and narrow tests before adopting them.

## Tool overlap and interpretation

The repository already loads Oxlint plus custom and ShadCN plugins through `vite.config.ts:125–126`. Its custom rules include canonical Node imports, global process platform reads, inline schema compilation, manual Effect test runtimes, Hermes compatibility, Uniwind theme restrictions, and native `title` tooltips (`oxlint-plugin-t3code/index.ts`; configured around `vite.config.ts:165–169,197–204,263–296`). ShadCN rules also check UI restyling, unknown classes, raw colors, and arbitrary values. Those are local syntax/platform/UI checks; they do not overlap most transitive package boundaries.

Knip is already run from `package.json:30–32`; it checks unused files/exports/dependencies and does not replace dependency-direction rules. The repository also has Macroscope conventions for Effect services, so service namespace and transport policy has a review-based counterpart. [`research.md`](../../research/notes/tooling.md) names dependency-cruiser, Sheriff, and Nx as existing architecture-policy baselines; avoid describing graph cycle or import-boundary checks as novel capabilities. The CLI’s proposed value is one reusable, resolved project snapshot for T3-specific policies, with limits stated for lexical origins and path-based exceptions.

## Evidence accounting

Use historical examples as evidence for individual policies, not as a proxy for ruleset quality. Strong reproductions here are the cycle fixed by #13151 and the namespace-import changes from #14385/#14387/#14389. The importer-caller restriction from #14018 is tested as a synthetic policy mutation, not a historical failure replay. PR #14385/#14387/#14389 support service import provenance and normalization, while #10122 supports shared-client ownership through a concrete extraction. The V2 service-placement and migration PRs do not show that every default graph edge was previously a bug. Some default entries are forward-looking architecture policy derived from `AGENTS.md` and `docs/internals/overview.md`; the three experimental entries have no confirmed historical failure in this evidence set.

## Running and adopting policies

Run `archguard check --root /path/to/t3code --config /path/to/irudd-ts/examples/t3code/profiles/t3code.json --json`. Configuration paths resolve from the invoking directory; selectors apply inside the chosen root. Run mobile iOS and Android profiles separately. Profiles are independent configurations, not automatically combined. Start with reviewed policy groups and exceptions that match the repository revision.

The source checkout inspected here is T3 main `e0db2a5e58bcbe7d738bca7667d2440ddb83e30f`. Historical V2 cases use their own exact revisions; they do not imply those paths exist on current main. The initial uninstalled checkout scan selected 3,908 TypeScript files and 29,225 imports across apps, packages, infra and scripts. It was incomplete: inherited `expo/tsconfig.base` and `astro/tsconfigs/strict` could not resolve, and generated desktop files were absent. The checker returned exit 2. These presets are adoption candidates, not a claim that current T3 passes all policies. Install required configuration packages and generate referenced files before treating a whole-project result as complete.

An excluded test or platform file can still be an imported dependency. Scan selectors do not compute dependency closure; exclusion of a referenced source target makes the graph incomplete. Mobile profiles match the reviewed test's source resolution order but do not implement Metro or every bundler option.

The default preset was also exercised on this main checkout: 2,531 selected files, 19,465 imports, exit 2 and 3,987 analysis problems. It emitted 239 provisional policy findings: 237 existing namespace-import conventions, one persistence-directory dependency and one direct filesystem import. These are not 239 confirmed bugs. The decider dependency path reaches `persistence/Errors.ts`, which establishes the proposed directory restriction but does not establish IO. See [the scan summary](https://github.com/alundgren/irudd-ts/blob/194bf91ce887498bf798cff2163d51bd897aa942/research/t3code/results/policy-scan-summary.json) for configuration and executable hashes, rule counts and representative paths. Full installed-project coverage and policy calibration remain adoption work.
