# Facts for repository enforcement

Research captured 2026-10-03 through two web scouts and primary documentation checks. This is a broad category inventory, not a claim to list every analysis fact ever used in software. No new dependency or upstream rule code was added.

This iteration adds repository roles. Next, prioritize actual registration references and package dependency kinds. They address mistakes agents make when adding files, and avoid the cost of general program analysis. The working role simulation is documented in [repository structure](../../docs/guides/repository-rules.md).

Schema compatibility and compiler-derived Effect requirements would provide different guarantees, but both need explicitly versioned providers and configuration. General taint, concurrency and resource analysis are much larger projects. A lexical imported call or module path cannot substitute for those analyses.

Roles are configured policy derived from paths. A path ending in `handlers.ts` establishes a selected role, not that its function validates input or implements every operation. Keep that distinction when adding framework adapters.

# Compiler analysis

Archguard records file, import/export, lexical call, service, package, and resolved module-graph facts. These source facts do not imply compiler types or runtime behavior. The optional [TypeScript 7 provider](../../docs/extensions/semantic-provider.md) now supplies separately versioned compiler contexts, receiver type states, named members, symbols and diagnostics for public dot accesses and JSX member tags. The broader analyses below remain distinct capabilities. The tools below show additional facts that can support stronger rules. Their analyses vary by language, build context, and configuration; each proposed fact should retain provenance and a completeness/status indicator so an unknown result cannot silently look clean.

## Fact inventory

| Fact category | Useful facts and enforceable rules | Cost and evidence limits | Examples |
|---|---|---|---|
| Syntax and source positions | Nodes, operators, modifiers, declarations, annotations, literals, and source ranges. Ban forbidden syntax, require explicit modifiers, spot suspicious constructs. | Lowest compiler-facing tier; syntax alone cannot distinguish same-spelled identifiers or resolve overloads. | Roslyn syntax trees; Error Prone tree matchers. |
| Lexical/symbol binding | A reference resolves to a declaration; declared and referenced symbols, scope, overload target, visibility, inheritance, and referenced metadata symbols. Enforce calls to specific APIs, layering by actual type/package, override requirements, or use of deprecated/forbidden members. | Requires language front end and often project/build references. Missing references, generated code, or conditional compilation can reduce coverage. | Roslyn semantic model maps names to symbols and supports source plus metadata; Error Prone checkers run over compiler trees and can inspect attributed declarations. |
| Resolved expression and declared types | Static type of an expression, generic arguments, conversions, nullable/annotated types, assignability, and overload resolution. Ban unsafe conversions, enforce API contracts and nullness, require allowed types at boundaries. | Type facts are only as sound/complete as the compiler configuration and annotations. A type does not by itself establish a runtime value or behavior. | Roslyn semantic model exposes expression type; Checker Framework adds compile-time qualifier types such as `@NonNull` and `@Nullable`. |
| Control flow | Basic blocks, branch edges, exceptional exits, reachability, and branch conditions. Enforce return/cleanup paths; verify all branches validate input or release a resource. | Requires control-flow graph (CFG) construction and transfer rules; exceptional paths and language constructs matter. | Roslyn exposes CFG blocks and branches; CodeQL exposes control-flow nodes/edges. |
| Intra-procedural data flow | Definitions/uses, read/write sets, reaching values, null refinement, constant/range facts, and resource state at each point. Detect reassignment, unchecked dereferences, use before initialization, invalid bounds, missed disposal. | Moderate/high implementation cost: abstract domains, joins at branches, loops, and language-specific operators; precision depends on aliasing and exceptional behavior. | Roslyn `AnalyzeDataFlow` provides read/write facts; Checker Framework refines types after guards, tracks constants/ranges, resource obligations, and lock state. |
| Interprocedural data flow and call graph | Candidate call targets, argument-to-parameter and return-to-call flows, field flows, and procedure summaries. Enforce that sensitive input is validated before a sink, or that forbidden APIs are reachable through wrappers. | High cost: virtual/dynamic dispatch, reflection, callbacks, libraries without source, aliasing, and graph size make call targets/data flow approximate. Preserve incomplete/imprecise states. CodeQL explicitly distinguishes local from more expensive global data flow. | CodeQL has `getTarget` versus possible actual callees; global flow crosses calls/fields. Clang Static Analyzer is path-sensitive and interprocedural, with cross-translation-unit options. |
| Taint / trust flow | Source, propagator, sanitizer/barrier, sink, and optional taint kind/flow state. Enforce SQL/HTML/command injection and trust-boundary policies. | Depends on correct source/sink/library models and sanitizer semantics. Interprocedural and inter-file tracking costs more; missing models produce false negatives, broad models create false positives. | CodeQL taint tracking extends value flow with influence steps; Semgrep offers source/sink/sanitizer/propagator patterns, with interprocedural and inter-file capabilities subject to product/language limits. |
| Effects and resources | Function effects such as allocation, blocking, throwing, I/O, lock acquire/release; obligations such as close/dispose; capabilities required/held at a program point. Enforce nonblocking/nonallocating contexts, disposal, lock protection, and thread-affinity annotations. | Needs trusted summaries/annotations for APIs, path-sensitive state, and policy for exceptions/ownership transfer. Some analyses are intentionally intraprocedural or conservative. | Clang thread-safety attributes check guarded data and lock requirements; its effect analysis checks `nonblocking`/`nonallocating`; Checker Framework includes Resource Leak and Lock Checkers. |
| Annotations and contracts | Declared nullness, ownership/must-call obligations, lock requirements, purity/effects, taint roles, API pre/postconditions. Enforce consistent contracts and validate implementations/callers against them. | An annotation is an input claim, not evidence by itself. Need validate bodies where available, report unchecked/external contracts, and track contract provenance. | Roslyn symbols include declared metadata; Checker Framework checkers use type/method annotations; Clang uses attributes for thread/resource facts. |
| Constant evaluation and ranges | Literal/constant values, propagated values, integer ranges, array lengths, and safe compile-time execution of declared pure methods. Enforce bounds, valid flags/keys, safe array access, and prohibit dangerous constant configurations. | Loops, overflow, language coercions, reflection, and side effects constrain evaluation. Explicitly track unknown/top and overflow policy. | Checker Framework Constant Value Checker propagates values and ranges; Roslyn analyzer tutorial combines constant analysis and data flow to identify immutable locals. |
| Concurrency facts | Lock/capability state, guarded fields, required thread or executor, conflicting accesses, lock ordering, and possible races. Enforce synchronization/affinity rules and flag deadlock/race patterns. | Static concurrency reasoning is difficult; annotations and modeled synchronization APIs are often needed. State clearly whether analysis is intra- or interprocedural and which schedule assumptions apply. | Clang Thread Safety Analysis checks held capabilities and guarded accesses, but documents that it is not interprocedural; Checker Framework also includes a Lock Checker. |
| Architecture dependencies | Type/package dependencies, member calls/accesses, inheritance, cycles, layers, and slices. Enforce allowed dependency direction, package ownership, no cycles, and API boundaries. | Usually much cheaper than general data-flow analysis; facts depend on class/source discovery and bytecode or module resolution coverage. Does not imply runtime execution reachability. | ArchUnit imports bytecode into class/dependency objects and checks package/class dependencies, layers, and cycles. |

## Practical progression for Archguard

1. Add compiler syntax, symbol binding, and expression-type facts through a language-specific provider. Keep policy in rules, as with existing facts. Add build-context identity and explicit incomplete/error states before presenting type-derived rules as complete.
2. Add reusable CFG and local data-flow facts next. They support distinct practical rules (branch validation, reassignment, constant/range checks) and can be tested with a violation, a corrected case, and negative controls.
3. Treat interprocedural call/data flow, taint, ownership, and concurrency as separate analysis capabilities with explicit limits and summaries. Avoid implying a lexical call edge proves the callee executes or that an approximate call graph is complete.
4. Require every rule to name its required facts and fail as an incomplete check when parsing, resolution, or analysis leaves required facts unavailable. Keep each import/call and its status visible, consistent with Archguard’s current contract.

Roslyn documents that a seemingly simple “make this local const” check needs syntax, constant evaluation, and data flow, illustrating why rule capability should be explicit. CodeQL documents that global flow has challenges from absent library source, dynamic targets, aliasing, and graph size; its local flow can be faster and sufficiently precise for many checks. Clang documents explicit limits of its thread safety and effect analyses. These are useful signals for staged adoption and honest reports, rather than claims that any one engine supplies universally complete program behavior.

## Rule and engine licensing are separate questions

Review the license of the analysis engine, query/rule repository, bundled database/schema, and any copied fixtures independently. GitHub states that the CodeQL standard libraries and queries repository is MIT-licensed while the CLI/engine is separately licensed, with usage restrictions for closed-source analysis absent a commercial license. Semgrep’s engine repository states LGPL-2.1, while Semgrep says its maintained rules use the separate Semgrep Rules License. Therefore neither an engine’s license nor permissive query source implies that every bundled rule set is permissively reusable. For Archguard, implement independently from public behavior/docs; do not copy upstream rule text, code, or fixtures without checking each applicable license and preserving required notices.

## Suggested order for Archguard

1. **Add configurable file roles and package/project tags to the current graph.** This enables test/source import bans, generated/test/schema boundaries, project ownership constraints, and required companion checks without requiring type information. Unknown or ambiguous role assignment should remain diagnosable.
2. **Model package public exports and dependency kinds.** Node's `exports` demonstrates that API visibility is a real enforceable package contract. This builds on existing module resolution but requires precise condition handling.
3. **Accept versioned schema facts through a plugin or external adapter.** Protobuf and OpenAPI/AsyncAPI checks have mature precedents; compatibility requires a declared baseline. Treat code-to-schema association as a separate, optional framework adapter.
4. **Ingest build graph facts from one explicit build-system adapter.** Target visibility and tags add data source imports do not contain, but a universal parser for build DSLs would be a large commitment.
5. **Keep database rollout, deployment/IaC, and pull-request owner enforcement outside the core source model initially.** They need SQL dialect/versioned baseline or normalized infrastructure/hosting state. A plugin can return findings through the existing trusted-plugin path while preserving explicit inputs and time limits.

# Runtime, test, time, and supply-chain enforcement facts

Research captured 2026-10-03. Runtime and test records describe executions that occurred under selected conditions. They do not establish that every possible program path behaves that way. ## How to represent lifecycle coverage

For execution-derived records, attach the artifact or source revision, tool/version, workload or test suite, environment, timestamp window, sampling/completeness indicators, and status. Report “observed in N scenarios/traces” separately from “static source property” and “model checked under declared bounds.” A missing runtime record should be treated as unknown coverage unless the collection system explicitly guarantees complete capture for the relevant workload.
