Your linter checks files and imports. Archguard checks how your repository fits together.

Write down the rules your team already agrees on: which code may reach which, and which files belong together. Run Archguard on each change, and drift shows up in the change that causes it.

Keep Oxlint. Add Archguard.

Oxlint already covers

  • Correctness and style rules inside each file
  • Banning an import by name (no-restricted-imports)
  • Import cycles (import/no-cycle)
  • Type-aware rules

Archguard can also ban imports and find cycles. If Oxlint already does that for you, keep it that way.

Archguard adds

  • Paths, not just imports

    Block client code from reaching server code, even through shared files.

    Keep server code out of the client

  • Package borders

    Imports go through a package's public entry. A package keeps its dependency list clean.

    Make other code use a package's public entry · Keep a package's dependency list clean

  • Where calls may happen

    Flag domain code that imports a module calling Effect.runPromise, directly or through a helper.

    Keep runtime calls at the edge

  • Repository structure

    Every file has a role. Files that belong together exist together. New migrations get registered.

    Give every file a known role · Require files that belong together · Never forget to register a migration

  • Your own rules

    Write rules in TypeScript or Rust over the same resolved graph.

    Write your own rule over the whole graph · Enforce a team import convention

  • Test and copy-paste review

    Find code edits your tests don't notice, and functions that were copied and renamed.

    Find code changes your tests miss · Find copy-pasted logic

Using dependency-cruiser or eslint-plugin-boundaries? Their path and package rules overlap with the first two items. The structure rules, your own graph rules, and the review tools are what Archguard adds there.

A pass you can trust

A file that fails to parse or an internal import that can't be resolved never turns into a quiet pass.

Check whether your tests notice small mistakes

Mutation testing checks your tests by changing the code they run. Archguard first runs your test command against unchanged source, then makes one small edit in an isolated copy and runs the tests again.

For example, changing subtotal >= 100 to subtotal > 100 changes what happens at 100. An assertion failure shows your tests caught the edit. If they still pass, that boundary may need an assertion. Review surviving edits before adding tests; some preserve behavior.
